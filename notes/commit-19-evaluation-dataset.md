# Commit 19: Expanded Evaluation Dataset for Robust PII Testing

This notes document details the construction and verification of our expanded, manually annotated evaluation dataset.

---

## 1. Why the Original 100% Metrics Were Insufficient

In our previous baseline, the system achieved a perfect `1.0000` F1-score. However, this dataset contained only 11 examples with approximately one positive example per PII type.
* **Under-representing formatting variants**: PII comes in many shapes (e.g., date formats, spacing/separator variants, punctuation styles). A single example per category cannot validate that the detectors can generalize.
* **Lack of challenging negative contexts**: Without complex negative examples (like ticket numbers or transaction IDs), we could not ensure that our precision safeguards were robust against false positive triggers.
* **Overfitting risk**: A small evaluation set creates the risk of unconsciously optimizing the pipeline to match only those specific test strings, rather than building a generalized, production-ready solution.

---

## 2. What Ground Truth Means

Ground truth is the absolute reference standard of what is *actually* PII in the dataset, manually defined by the system's human architects. 
* **Authoritative Reference**: Ground truth represents the ground truth author's decision, independent of any detector output.
* **Not Generated by Detectors**: We never run the detector pipeline and copy its outputs directly into `ground_truth.json`. That would treat the detector's predictions as absolute truth, hiding its errors.
* **Anchor for FP/FN Calculation**: Without a clean, independent ground truth, we cannot calculate true positives, false positives, or false negatives correctly.

## 3. Dataset Construction & Required PII Types

The dataset is stored in [evaluation/ground_truth.json](file:///Users/piyushsengar/Desktop/pii-redaction-tool/evaluation/ground_truth.json) and covers all 9 required types with at least 5 positive examples each:

| PII Type | Examples Count | Variation Strategy |
| :--- | :--- | :--- |
| **PERSON** | 11 positive entities | Full name pairs, middle initials, prefix titles (`Mr.`, `Dr.`), single names. |
| **EMAIL** | 7 positive entities | Standard suffixes, subdomains, alias symbols (`+`), personal/corporate domains. |
| **PHONE** | 6 positive entities | Spaces, hyphens, prefixes (+91, std codes), 10-digit formats. |
| **ORGANIZATION**| 6 positive entities | Company suffixes (`LLC`, `Inc.`, `Corp.`, `Ltd.`, `Technologies`). |
| **ADDRESS** | 6 positive entities | US and international street levels, apartment numbers, ZIP codes. |
| **SSN** | 6 positive entities | Dashed standard structures, including synthetic ranges like `999-00-xxxx`. |
| **CREDIT_CARD** | 6 positive entities | Separated by spaces, hyphens, or compact digits; Visa Luhn-compliant values. |
| **DOB** | 6 positive entities | Standard slash, hyphen, dot separators, and textual month layouts (e.g. `31 Dec 1985`). |
| **IP_ADDRESS** | 6 positive entities | Internal, external, loopback IPv4 addresses. |

## 4. Positive vs Negative Examples

### Positive Example
* **Sentence**: `"The report was signed by Mr. David K. Miller."`
* **Annotations**: `David K. Miller` is a positive `PERSON` entity. It has supporting context (`"signed by Mr."`).

### Negative Example
* **Sentence**: `"Transaction reference number 123-45-6789 is not an SSN."`
* **Annotations**: `123-45-6789` is annotated as `non_pii` of type `SSN`. It resembles an SSN structurally, but is placed in a negative context (`"Transaction reference number"`) which should trigger a resolver rejection.

## 6. Evaluation Limitations

1. **Synthetic Scope**: The benchmark is synthetic and controlled. It cannot completely capture the full formatting variability or noise of real-world DOCX files.
2. **Exact character matching**: Offsets must match exactly. Overlapping but slightly shifted offsets count as both a False Positive and a False Negative.
3. **Subjective Ground Truth**: Human taggers might disagree on boundaries (e.g. whether to include `"Dr."` or `"LLC"` in the span).
