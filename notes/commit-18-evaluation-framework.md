## 1. Commit Overview

### Why Evaluation is Necessary
In machine learning and PII redaction, we cannot measure progress or safety without metric data. An evaluation framework provides reproducible numbers showing how many PII items were successfully redacted, how many were missed, and how many non-PII items were incorrectly modified.

### Why Detector Output Cannot Be Used as Ground Truth
We cannot evaluate a detector using its own outputs as the correct answers. If a detector has bugs or misses half of the entities, it will report 100% success on its own predictions. True evaluation requires an independent benchmark.

### What a Manually Annotated Dataset Means
A manually annotated dataset is a set of text examples where a human expert has carefully read the text and marked every PII item and ambiguous case, recording their exact character boundaries `[start, end)` and entity types.

### Difference between Prediction and Ground Truth
* **Ground Truth**: The objective reality or manual annotation (what *should* be detected).
* **Prediction**: The output generated by our pipeline/detectors (what *was* detected).

## 4. Metrics

* **True Positive (TP)**: A correct prediction. Predicted type and character span match ground truth exactly.
* **False Positive (FP)**: An incorrect prediction. The system predicted PII on text that is not PII.
* **False Negative (FN)**: A missed entity. The system failed to predict an actual PII item.
* **True Negative (TN)**: An ambiguous non-PII item that the system correctly rejected (was not predicted as PII).

### Mathematical Formulas

$$\text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}}$$

$$\text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}}$$

$$\text{Accuracy} = \frac{\text{TP} + \text{TN}}{\text{TP} + \text{TN} + \text{FP} + \text{FN}}$$

$$\text{F1} = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

### Simple Numerical Example
Suppose our evaluation run has:
$$\text{TP} = 8, \quad \text{FP} = 2, \quad \text{FN} = 1, \quad \text{TN} = 3$$

1. **Precision**:
   $$\text{Precision} = \frac{8}{8 + 2} = 0.8 \quad (80\%)$$
2. **Recall**:
   $$\text{Recall} = \frac{8}{8 + 1} = 0.889 \quad (88.9\%)$$
3. **Accuracy**:
   $$\text{Accuracy} = \frac{8 + 3}{8 + 3 + 2 + 1} = \frac{11}{14} = 0.786 \quad (78.6\%)$$
4. **F1-Score**:
   $$\text{F1} = 2 \times \frac{0.8 \times 0.889}{0.8 + 0.889} = 2 \times \frac{0.711}{1.689} = 0.842 \quad (84.2\%)$$

## 5. Precision vs. Recall

* **High Precision**: Few False Positives. This means the system makes very few unnecessary redactions, keeping clean formatting intact.
* **High Recall**: Few False Negatives. This means the system misses very few actual PII items, ensuring high security.
* **PII Redaction Preference**: PII redaction heavily prioritizes **recall** over precision. A missed email address or SSN (False Negative) is a security breach, whereas accidentally redacting a normal order number (False Positive) is just a minor formatting inconvenience.

---

## 6. True Negative Problem

* **Why TN is Difficult**: In typical binary classification, every non-entity character or word in a document could count as a True Negative.
* **The Artificial Inflation Issue**: If a document has 10,000 characters and we detect 5 PII items, calling all 9,995 other characters True Negatives would artificially inflate accuracy to $99.9\%$, even if our detector missed half of the actual PII!
* **The Project's Solution**: We define True Negatives **only** over explicitly annotated ambiguous negative spans (`non_pii` fields in `ground_truth.json`). This ensures accuracy remains a meaningful and realistic measure.

---

## 7. Exact Span Matching

For a prediction to be counted as a True Positive, it must match:
1. **Same entity type** (e.g. `EMAIL`)
2. **Same start character index**
3. **Same end character index**

```text
Ground Truth:  [10, 20) "john@a.com" (EMAIL)
Prediction A:  [10, 20) "john@a.com" (EMAIL)       ──> Matches! (TP)
Prediction B:  [9,  20) " john@a.com" (EMAIL)       ──> Mismatch (off by one space -> FP & FN)
Prediction C:  [10, 20) "john@a.com" (PERSON)      ──> Mismatch (wrong type -> FP & FN)
```

**Why exact matching is strict but reproducible**: Exact matching is a strict metric because even a minor character shift (like including a trailing space or comma) is penalized. However, it is fully automated, deterministic, and leaves no room for human interpretation during evaluations.

---

## 8. Per-Type Metrics

Evaluating overall performance is not enough, as different PII types behave differently:
* **`EMAIL`**: Typically has extremely high precision and recall due to predictable regex patterns.
* **`PERSON`**: Often has lower precision and recall due to spaCy NER context variations.
* **`DOB`**: May have lower recall because context rules reject dates that resemble agreement dates or incorporation dates.

Analyzing per-type metrics helps identify exactly which detectors need tuning.

## 9. Testing

We created **[tests/test_evaluator.py](file:///Users/piyushsengar/Desktop/pii-redaction-tool/tests/test_evaluator.py)** to assert:
* **Perfect Predictions**: All metrics equal `1.0`.
* **Single False Positives/Negatives**: Precision and recall degrade correctly.
* **Wrong Entity Types**: Spans that match but have incorrect types count as both an FP and an FN.
* **Deduplication Checks**: Duplicate predictions for the same span are treated as a single prediction.
* **Zero Denominators**: Safe fallbacks return `0.0` when dividing by zero.
* **True Negative Accuracy**: TN accuracy is calculated correctly using the explicit `non_pii` spans.

## 11. Limitations

* **Small Dataset**: The initial dataset contains 11 synthetic examples, which does not cover all edge cases found in large documents.
* **Strict Exact Matching**: Shifts by a single character (such as including punctuation) are penalized as failures.
* **Model Dependency**: NER performance depends on spaCy model configurations.
* **Prospectus is Not Ground Truth**: Running the tool on the prospectus document is a smoke test; it cannot be treated as ground truth unless manually annotated.

## 12. Interview Explanation

**Question:** *"How did you evaluate your PII redaction system?"*

**Answer:**
> "I implemented a reproducible evaluation framework. We created a manually annotated synthetic ground truth dataset containing positive entities and ambiguous negative spans. We ran our pipeline to get predictions and matched them using exact span and type criteria to compute precision, recall, accuracy, and F1-score."

**Question:** *"Why can't you use your own predictions as ground truth?"*

**Answer:**
> "Because the system cannot grade its own exam. If the detectors contain bugs or miss entities, evaluating against our own predictions would hide those failures and report a false 100% success rate."

**Question:** *"What is precision?"*

**Answer:**
> "Precision is the ratio of true positive predictions to all positive predictions made by the system. It measures how many of our detections were actually correct."

**Question:** *"What is recall?"*

**Answer:**
> "Recall is the ratio of true positive predictions to all actual positive entities in the ground truth. It measures how many of the actual PII items were successfully found by the system."

**Question:** *"Why is recall important for PII redaction?"*

**Answer:**
> "A missed PII entity (False Negative) is a security breach, whereas an unnecessary redaction (False Positive) is just a minor formatting inconvenience. Therefore, we prioritize recall to ensure complete redaction."

**Question:** *"How did you calculate accuracy?"*

**Answer:**
> "Accuracy is calculated as (TP + TN) / (TP + TN + FP + FN). To make it meaningful, True Negatives (TN) are defined only over explicitly annotated ambiguous negative spans rather than all characters in the document."

**Question:** *"Why is accuracy potentially misleading?"*

**Answer:**
> "If we treated all non-PII characters in a document as True Negatives, the massive count of non-PII characters would overwhelm the equation. The accuracy score would approach 99.9% even if our detectors missed half of the PII. Limiting TN to explicit negative annotations keeps the metric useful."

## 13. Quick Revision

### 5 Key Concepts
1. **Evaluation** compares system predictions against manually annotated ground truth.
2. **Exact span matching** requires matching type, start index, and end index exactly.
3. **Recall** is prioritized in PII redaction to prevent security leaks.
4. **True Negatives** are limited to explicitly annotated negative candidate spans.
5. Overall metrics are **micro-averaged** over all categories.

### 3 Interview Questions
1. *Why is accuracy a misleading metric for PII detection if TN is not constrained?*
2. *What is the difference between a False Positive and a False Negative in PII redaction?*
3. *Why does exact matching count a shifted character span as both an FP and an FN?*

### 3 Practical Examples

#### Example 1: Precision Calculation
* **Ground Truth**: `[A]`
* **Predictions**: `[A, B]` (A is correct, B is a false positive)
* **Precision**: $1 / (1 + 1) = 0.5 \quad (50\%)$

#### Example 2: Recall Calculation
* **Ground Truth**: `[A, B]`
* **Predictions**: `[A]` (B is missed)
* **Recall**: $1 / (1 + 1) = 0.5 \quad (50\%)$

#### Example 3: True Negative
* **Text**: `"Order 1234"` (looks like a credit card number but is not).
* **Ground Truth**: Non-PII span `"1234"` (type: `CREDIT_CARD`).
* **Pipeline Prediction**: Rejects the candidate (no prediction made).
* **Metric**: Counts as **1 True Negative (TN)** for the `CREDIT_CARD` category.
